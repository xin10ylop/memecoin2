## Findings

### On a constant-product curve an immediate round trip costs exactly 2f - f^2, independent of size: price impact cancels perfectly. Symmetric 'slippage penalties' in a backtest model a cost that does not exist.

Proof for the pump.fun convention (fee off input on buy, off output on sell, only net enters curve). Buy dx: e=dx(1-f) enters, tok = y*e/(x+e), x'=x+e, y'=y-tok=xy/x'. Sell tok: y'+tok = xy/x' + y*e/x' = y(x+e)/x' = y, so gross = x'*tok/y = e. Net received = e(1-f) = dx(1-f)^2. Round-trip cost = 1-(1-f)^2 = 2f-f^2 exactly, for ANY dx. At pump.fun f=0.0125 that is 2.4844%. Verified numerically across sizes 0.05-5.0 SOL on a 15.35 SOL pool: correct model returns 2.484% at every size. The real costs of size are elsewhere: (a) entry basis inflation - your own buy sets p_avg above mid so every subsequent multiple is measured from a worse denominator; (b) reserve depletion between entry and exit - if SOL reserve falls from x to alpha*x your exit realizes proportionally less at the same token price; (c) path dependence of sliced exits; (d) counterfactual contamination - your fill permanently perturbs curve state that the recorded price path does not contain.

**Actionable:** Delete any flat symmetric slippage parameter. Charge exactly 2f-f^2 for the venue fee component and model the four real size costs explicitly: track your own entry p_avg as the cost basis (not mid), re-read pool reserves at exit time from the snapshot rather than assuming entry-time depth, and simulate sliced exits sequentially applying each fill to the pool state.

### BUG in /home/user/memecoin2/src/degen/sim/amm.py: Pool.apply() credits the full qty_in including the fee to the reserve, so your own fee re-enters the curve and partially refunds you at exit. The understatement grows monotonically with trade size, giving a size optimizer a spurious economy of scale.

apply() on a buy does `Pool(self.sol_reserve + fill.qty_in, ...)` while cp_out() computed the output using eff_in = qty_in*(1-fee). The fee therefore inflates the reserve you later sell into. Measured on a 15.35 SOL pool (your median young-token depth) at f=0.0125, code round-trip vs correct round-trip: 0.05 SOL 2.477% vs 2.484% (-0.008pp); 0.25 SOL 2.446% vs 2.484% (-0.039pp); 0.5 SOL 2.408% vs 2.484% (-0.076pp); 1 SOL 2.336% vs 2.484% (-0.148pp); 2 SOL 2.204% vs 2.484% (-0.280pp); 5 SOL 1.885% vs 2.484% (-0.599pp). Direction matters more than magnitude: bigger trades look CHEAPER, which is backwards, so any sizing search will push size up. Analytically the code's ratio is (1-f)^2*(X+e)/(X+(1-f)e) which exceeds (1-f)^2. Note the distinction: for Raydium CPMM the LP fee genuinely IS retained in the pool so crediting full qty_in is correct there; for pump.fun the protocol+creator fee is transferred OUT to fee recipients and must not enter the curve.

**Actionable:** Make fee routing a Pool attribute. Add `fee_to_reserve: bool` — True for Raydium CPMM / PumpSwap LP fee (20bps), False for pump.fun protocol+creator fee. When False, apply() must credit qty_in*(1-fee) on buys and debit the gross SOL out on sells with the trader receiving gross*(1-fee). Add a unit test asserting round_trip_cost == 2f-f^2 within 1e-9 for pump.fun at pool fractions 0.1%, 1%, 10%, 30%.

### Exact Raydium CPMM swap math, verified from program source, with the fee applied to the input before the curve.

swap_base_input_without_fees: numerator = input_amount * output_vault_amount; denominator = input_vault_amount + input_amount; output = numerator/denominator, i.e. dy = (dx * y)/(x + dx). swap_base_output_without_fees: numerator = input_vault_amount * output_amount; denominator = output_vault_amount - output_amount; input = ceil_div(numerator, denominator), i.e. dx = ceil((x * dy)/(y - dy)). Invariant maintained: (x + dx)(y - dy) = xy. Fee is taken off the input first, so with fee fraction f the realizable fill is dy = ((1-f)dx * y)/(x + (1-f)dx). Derived quantities: p_avg = dx/dy = (x + (1-f)dx)/(y(1-f)); p_mid = x/y; impact ratio p_avg/p_mid = (x + dx(1-f))/(x(1-f)); slippage s = [dx(1-f) + f*x]/(x(1-f)). Max input for average impact m: dx_max = x*[(1+m)(1-f) - 1]/(1-f), which requires m > f/(1-f) (at f=1.25% no trade of any size achieves impact below 1.27%). Your max_size_for_impact() implements this correctly — I re-derived it and it matches. PumpSwap fees verified from pump-public-docs GlobalConfig: lp_fee_basis_points == 20 bps, protocol_fee_basis_points == 5 bps, total 25 bps, charged on buy/sell but not deposit/withdraw; creator fees are documented separately and I did not verify their rate.

**Actionable:** Use dy = ((1-f)dx*y)/(x+(1-f)dx) as the single fill primitive for CPMM/PumpSwap/graduated pools. Use integer u128 arithmetic with ceil_div on the base-output path if you ever need exact-out quoting, since off-by-one in the last decimal is the difference between a landed and a reverted transaction at tight slippage.

### Deflated Sharpe Ratio and expected-maximum-Sharpe formulas, verified verbatim from the Bailey & López de Prado source PDF — but Sharpe is the wrong statistic for your payoff (skew 35.7, kurtosis 1,581).

### Concrete backtest architecture: a five-layer pipeline in which each layer can only lose information, with a counterfactual-contamination guard at the fill layer.

LAYER 1 CENSUS (append-only, never filtered). Every discovered mint with discovery timestamp and source, including mints that never produced a price. This is the denominator for every base rate. Never JOIN away from it; LEFT JOIN onto it. LAYER 2 EVENT LOG (swap-level, the missing piece). Every swap on every tracked pool: slot, signature, signer, direction, amount_in, amount_out, and post-swap reserves. Reserves after each swap are the ground truth the whole simulation needs; price series are a lossy derivative. Until this exists, latency, partial fills, and impact are all unmodelable. LAYER 3 REPLAY. Deterministic, seeded, single-threaded per token. For each token, step through the event log slot by slot maintaining pool state. On a signal at slot s: draw L_slots from the empirical latency distribution; advance the pool by applying every real swap in [s, s+L); draw transaction success from the volatility-conditioned hazard; if it succeeds, compute the fill with the exact CPMM formula against the reserve state at s+L; APPLY your own fill to the pool state and keep it applied. LAYER 4 COUNTERFACTUAL GUARD. This is the piece almost everyone omits. After your fill, the recorded event log continues to contain the swaps that really happened in a world where you did not trade. Track a divergence metric d = |your cumulative reserve perturbation| / current reserve; when d exceeds a threshold (start at 0.02), stamp the trade `counterfactual_invalid=True` and report those trades' PnL separately. A backtest where 60% of trades are counterfactual-invalid is telling you your size is too big for the data to support any conclusion. LAYER 5 EVALUATION. CPCV over time-block groups with interval purge and embargo; per-path metric distribution; random-selection null band at matched trade count; Romano-Wolf max-statistic correction across all configs tried. CROSS-CUTTING: one immutable config hash per run, every run appended to a trials ledger (this is where N for multiple-testing correction comes from — if it is not logged, N is unknowable and every correction is a guess).

**Actionable:** Build in this order, because each unlocks the next: (1) the trials ledger (one afternoon, and it is the prerequisite for any honest significance claim); (2) the random-selection null band in summarize() (one afternoon, immediately reprices every result you already have); (3) full-census base rates via LEFT JOIN off the registry (one day); (4) the swap-level event log (the big one, but nothing about latency or impact is real without it); (5) CPCV once the census spans multiple days. Note that steps 1-3 cost ~2 days and will likely show your current results are noise — do them before investing in step 4.
