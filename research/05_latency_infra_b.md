# Solana low-latency execution infrastructure for a memecoin sniping/trading bot: providers, priority fees, Jito tips, compute budgets, detection paths, landing rates, colocation, and MEV/sandwich risk on buys

## Executive summary

URGENT, TIME-CRITICAL: Jito ShredStream is deprecated and shuts down 2026-09-05 — 13 days from today (2026-08-23). If your design assumes ShredStream, it is already dead. Jito's own docs point to DoubleZero Edge (multicast shreds, $30–100 USDC per device per epoch ≈ $450–1,500/mo); OrbitFlare ShredStream and AllenHark Shreds are drop-in raw-UDP alternatives. Second structural change: SIMD-0286 raised the block limit from 60M to 100M CU on 2026-07-29 (epoch 1009), but the 12M CU per-writable-account-per-block cap was NOT raised — that cap, not the block cap, is what throttles you when 500 bots hit the same pump.fun bonding curve. At ~80k CU per buy, roughly 150 buys can land per block against one curve; everything else is dropped regardless of fee. I measured live tip and CU data rather than quoting blogs. Jito tip floor on 2026-08-23 (three samples, 13 min apart) was p50 3,511–6,602 lamports, p75 7,128–41,750 lamports, p95 92,676–750,000 lamports — note the p75 swung 6x and p95 swung 8x within thirteen minutes, so any hardcoded tip is wrong within minutes; poll https://bundles.jito.wtf/api/v1/bundles/tip_floor or the tip_stream websocket. SOL was $95.27, so the p95 tip is ~$0.071 — trivially cheap relative to a snipe, which means tip is not your cost constraint and you should bid aggressively (p95–p99, 100k–750k lamports) for contested launches. I measured compute units from real mainnet transactions: pump.fun bonding-curve buy = 58,887–91,305 CU when the ATA already exists, ~102,351 CU when the buy creates the ATA; pump.fun sell = 64,931–73,938 CU; PumpSwap bare swap = 21,125–21,686 CU (very tight cluster), 26,160–59,172 CU with ATA/wSOL handling; Raydium AMM v4 swap = 48,200 CU and 53,631 CU in two tight clusters. Nearly every bot on chain over-requests: I saw CU limits of 400,000 and 1,400,000 set on transactions that consumed 135k. Over-requesting wastes nothing in fees (you pay on requested CU × price, so it directly overpays) and worsens your block-packing position — set the limit to measured p95 + ~20%, not 200k/400k defaults. On detection: Yellowstone/Dragon's Mouth gRPC beats WebSocket decisively — Triton's own published measurement is slot updates p90 ~5ms via gRPC vs ~150ms via RPC polling, and account updates p90 ~215ms via gRPC vs ~374ms via native WebSocket. Helius LaserStream's preprocessed shred delivery claims ~8ms ahead of the `processed` commitment. logsSubscribe is the worst option and should not be in a production snipe path. Colocation is not optional: Europe produces 68.5% of leader slots (Frankfurt 19–26%, Amsterdam 16–25%, London 12%), TeraSwitch hosts ~59% of validators, and the lowest measured QUIC handshake to a validator is 965µs from an in-datacenter probe versus 60–75ms from AWS Ashburn to New Jersey and 190–220ms Singapore-to-EU. A US-hosted bot loses the race on physics before any code runs. On MEV: sandwiching is real and memecoin-concentrated — 16 of the top 20 sandwiched tokens were pump.fun tokens, ~51,600 attacks/day at 88.9% success, average extraction 0.0425 SOL ($8.67 at the time of that report) per attack. Your slippage cap IS the attacker's budget: 1% slippage on a $10,000 buy hands over up to $100. The single highest-leverage mitigation is not a wider slippage number but computing an exact minAmountOut from the bonding-curve/pool reserve state you already read at detection time, then submitting via a Jito bundle (never publicly broadcast) or a private relay. Sources materially disagree on three points I flag below: Helius Sender's minimum tip (docs say 0.001 SOL, Helius's own blog and the widely-used sol-trade-sdk say 0.0002 SOL), 0slot's minimum tip (0.001 SOL on lower tiers, 0.0001 only on Advanced — the SDK hardcodes 0.0001 and will get your transactions silently dropped), and whether priority fees/Jito tips help at all (Chorus One's Nov-2024 study says negligible; that study measured ordinary 90-second-window transactions, not same-slot auctions, and does not generalize to sniping).

- **MAX_CU_PER_TRANSACTION** = `1400000` — Solana protocol maximum per transaction.
- **DEFAULT_CU_PER_INSTRUCTION_IF_UNSET** = `200000` — Solana's default when no setComputeUnitLimit is present. Builtin instructions default to 3,000 CU. Always set the limit explicitly.
- **BASE_FEE_LAMPORTS_PER_SIGNATURE** = `5000` — Split 50/50 between burn and validator. This is the cost of a failed snipe — cheap enough that failing on a bad price is always better than filling on one.

- **BLOCKHASH_VALIDITY_SLOTS** = `150` — ≈60 seconds nominal. For a snipe this is a liability, not a feature — set your own abort deadline at 2-3 slots.
- **SNIPE_ABORT_DEADLINE_MS** = `1200` — 3 slots. After this the price you computed at detection is stale; treat a later fill as unwanted and exit immediately.
- **DETECTION_TO_WIRE_SLO_P99_MS** = `50` — Published component budget: gRPC reception 5-20ms co-located + decision <5ms + signing <1ms + submission 5-30ms. Co-located Frankfurt measured 35ms consistently versus 220ms without colocation.
- **GRPC_VS_WEBSOCKET_SLOT_LATENCY_P90_MS** = `5 (gRPC) vs 150 (RPC polling)` — Triton One's own published Dragon's Mouth figures. For account updates: ~215ms gRPC p90 vs ~374ms native WebSocket p90.
- **LASERSTREAM_SHRED_LEAD_OVER_PROCESSED_MS** = `8` — Helius LaserStream preprocessed shred delivery claim — data ~8ms ahead of the processed commitment level.
- **DOUBLEZERO_VS_JITO_SHREDSTREAM_P95_GAIN_MS** = `28` — Measured p95 improvement. Under congestion: up to 20ms in EU, 80ms in US, 100ms+ in Asia.
- **SKIP_PREFLIGHT** = `true` — Preflight simulation adds ~100ms — one quarter of a slot. Always skip on snipes; simulate offline at startup instead.

- **JITO_REGION_FANOUT_COUNT** = `9` — Jito's rate limit is 1 req/s per IP PER REGION. Fanning out across all 9 mainnet block engine endpoints gives ~9 req/s from a single IP at zero cost.

## Traps and failure modes

- JITO SHREDSTREAM DIES 2026-09-05 — 13 days from today. Any design, tutorial, repo or LLM answer that recommends it is already obsolete. Most content on the web still recommends it.
- sol-trade-sdk's minimum-tip constants are wrong for at least three providers (0slot 0.0001 vs actual 0.001 on most tiers; Nozomi 0.0001 vs actual 0.001; Stellium's own comment contradicts its constant). Nozomi SILENTLY DROPS underfunded transactions — no error, no signature, you think you sent and you did not. This is the single nastiest failure mode in the stack.
- Setting compute_unit_limit to 200,000 / 400,000 / 1,400,000 'to be safe' directly overpays the priority fee, because the fee is computed on the REQUESTED limit, not consumption. I measured live bots paying 6.7x too much on Raydium swaps this way. It also worsens your scheduler position against the 12M per-account cap.
- The 12M CU per-writable-account-per-block cap did NOT rise with SIMD-0286. At ~80k CU per buy, ~150 buys land per block against one bonding curve. Past that, no tip and no relay helps. Bots that assume 'pay more, land' will burn fees on transactions that were never going to fit.
- pump.fun and PumpSwap share the IDENTICAL buy discriminator bytes [102,6,61,18,1,218,235,234] and the identical sell bytes. Matching on discriminator without first resolving the program ID will misroute trades to the wrong venue.
- pump.fun now has v2 instruction variants (buy_v2, sell_v2, buy_exact_quote_in_v2) with different discriminators. A parser written only against v1 will silently miss a growing share of flow and under-report activity — the failure is invisible, not an exception.
- Jito's rate limit is 1 request/second per IP per region. A naive single-endpoint integration caps you at 1 attempt/sec, which loses every contested launch. Most tutorials never mention it.
- Hardcoding any Jito tip is wrong within minutes: I watched p75 move 7,128 → 41,750 → 10,000 lamports and p95 move 92,676 → 750,000 lamports across 13 minutes on a single ordinary day.
- getRecentPrioritizationFees returns the MINIMUM prioritization fee per slot, not a distribution of what competitive transactions paid. Its p50 of 0 is technically correct and completely useless for bidding. I measured 88% of slots returning zero.
- Chorus One's widely-cited finding that priority fees and Jito tips have 'negligible' latency benefit is from November 2024, measured ordinary transactions over a 90-second window, and predates SIMD-0286 and the current relay landscape. It does not generalize to intra-slot snipe auctions. Do not let it talk you out of tipping.
- Shred-based triggers fire on transactions that may never land or may fork away. Writing shred-derived events into your position ledger will corrupt state. Shreds are a speculative trigger; only confirmed-commitment gRPC is truth.
- Preflight simulation costs ~100ms — a quarter of a slot. Leaving skipPreflight at its default silently forfeits the race.
- Cold TCP/TLS handshakes to a submission endpoint can cost more than the entire tip. Helius publishes a /ping endpoint specifically for connection warming; if you do not keepalive, your first transaction after idle is your slowest.
- Running the hot path in Node.js: measured 450µs average and 2,100µs p99 parse time versus 12µs/18µs in Rust, plus 14 GC pauses per minute. A single GC pause can span a slot.
- Nozomi explicitly penalizes client-side retries — resubmitting wastes your rate limit AND reduces your priority. Generic retry-with-backoff middleware makes you slower there.
- Nozomi MEV Protect and similar trusted-validator whitelists are explicitly SLOWER with a higher blockhash-expiration rate. Turning on 'MEV protection' can cost you more in missed fills than it saves in sandwiches.
- A percentage slippage cap on a snipe is a standing offer to MEV bots equal to that percentage of your position. 20% slippage on a fresh launch means you have pre-authorized a 20% loss. Compute exact minAmountOut from reserve state instead.
- Jito bundle atomicity does not defeat 'wide' multi-slot sandwiches, which reportedly account for the majority of current sandwich activity. Bundles are necessary but not sufficient.
- The Jito tip must be in the LAST transaction of a bundle. Putting it first means it can be stolen on a fork and you pay even when the bundle fails.
- Not rotating tip accounts creates write-lock contention on a single hot account — the same mechanism that throttles you on the bonding curve. Jito publishes 8, Nozomi 17, Astralane 17 specifically for this; pick randomly per transaction.
- Provider benchmarks are almost universally published by the provider that wins them. Helius's benchmark ranks Helius first; OrbitFlare's ranks OrbitFlare first; RPC Fast's ranks RPC Fast first. The only trustworthy number is one you measured from your own colo.
- Chainstack scored 96.9% correctness in a cross-provider benchmark — a ~3% wrong-answer rate. For a bot that sizes positions off RPC reads, wrong answers are worse than slow answers.
- Chainstack's $49 gRPC tier caps at 2 streams and up to 50 accounts. A program-wide subscription may not fit; verify before committing or you will discover the cap in production.
- DoubleZero Edge requires GRE, BGP and PIM plus a public IPv4 and multicast. A standard cloud VM will very likely not work. Verify your host supports it before budgeting for Edge.
- Solana's upcoming v1 message format changes prioritization fees from price×limit to an absolute lamport total. Fee logic written today will need rework, and the current incentive to minimize CU limits changes with it. I could not verify an activation date.
- Helius's own docs and its own blog disagree on both the Sender minimum tip (0.001 vs 0.0002 SOL) and the Sender rate limit (50 TPS vs 6 TPS). When a vendor contradicts itself, build a startup self-test that empirically verifies the threshold rather than trusting either document.
- Blockhash validity of 150 slots (~60s) means a 'failed' snipe can land a minute later at a completely different price. Without an explicit abort deadline and a reconciliation path for late fills, you will hold positions you never intended to open.
- Tips are charged on landing by Nozomi but on bundle success by Jito — a landed-but-unprofitable Jito bundle still costs the tip. These are different risk profiles and should be modeled separately, not lumped as 'tip cost'.
- The '89% slot-0 landing rate', '20-60% upside between slot 0 and slot 2', '$370-500M extracted', and '93% of sandwiches are wide' figures all come from vendor content marketing or secondary aggregators with no published methodology. I could not verify any of them against primary data. Do not put them in a P&L model.

### The 12M CU per-writable-account-per-block cap — not the block cap — is the real sniping bottleneck, and it did not move when the block cap rose 66%

SIMD-0286 activated on mainnet 2026-07-29 at epoch 1009, raising max block compute from 60M to 100M CU (+66%). The maximum compute that may write to any single account within one block remains 12,000,000 CU, unchanged. Max block accounts-data-size delta remains 100MB. Per-transaction max is 1,400,000 CU; default per-instruction budget is 200,000 CU; builtin instructions default to 3,000 CU. Base fee is 5,000 lamports per signature, split 50/50 burn/validator. Prioritization fee = ceil(compute_unit_price × compute_unit_limit / 1,000,000) lamports. I verified epoch length live: slotsInEpoch = 432,000 (epoch 1021, absoluteSlot 441,185,271).

**Actionable:** A pump.fun bonding curve is a single writable account. At ~80,000 CU per buy, only ~150 buy transactions can land against that one curve per block (12M / 80k), regardless of what anyone pays. This means: (1) minimizing your CU limit literally increases the number of slots-worth of competitors you beat, since the cap is consumed in requested-CU order by the scheduler; (2) if you are not in the first ~150 accepted txs you do not land — no tip fixes it; (3) plan for slot-1 and slot-2 fallback entries with recomputed pricing rather than assuming slot-0 or nothing.

### Your slippage tolerance is literally the attacker's extraction budget — this is the single most important MEV parameter

The arithmetic is direct: a 1% slippage setting on a $10,000 swap means an attacker can extract up to $100. Setting 20%+ slippage means accepting a fill 20% worse than expected. Published slippage guidance by liquidity band: large-cap (SOL, BONK, JUP) 0.5-2%; mid-cap $5M-$50M 2-5%; small-cap/new meme $100K-$5M 5-15% ('trades often fail below 5%'); fresh launch/snipe <$100K 15-30%+. Guidance is to start at 3% and increment by 2%. Jupiter introduced Dynamic Slippage in Aug 2024 using heuristics over token type and pool/orderbook to compute a per-transaction threshold; Jupiter's Swap API exposes minBps/maxBps (documented example: minBps 50, maxBps 300) and a static example of 20 BPS. Jupiter Ultra V3 claims 0.6bps average POSITIVE slippage versus −1bps to −14bps on other top-5 trading terminals, and claims 34x better sandwich protection — achieved by running its own relayer on Jupiter validator stake and delivering to the leader within 0-1 blocks, bypassing public RPC.

**Actionable:** Do not use a percentage slippage cap on snipes. You already read the bonding-curve or pool reserve state at detection; compute the exact expected out and set minAmountOut = expected × (1 − ε) with ε small (50-150 bps), then let the transaction FAIL rather than fill badly. A failed snipe costs 5,000 lamports; a 20%-slippage fill costs 20% of position. The −1bps to −14bps range on competing terminals is the realistic quantification of sandwich cost per trade for a protected-but-not-private route; use −14bps as your pessimistic MEV assumption and 0bps for bundle-routed fills.

Solana docs note the upcoming v1 message format will change prioritization fees from the current derived model — ceil(compute_unit_price × compute_unit_limit / 1,000,000) lamports — to 'an absolute lamport total set in the message config'. No activation date was given in the documentation I read.

**Actionable:** Isolate fee computation behind a single interface with one implementation today (price × limit) so the v1 switch is a one-file change, not a refactor. Also note this removes the current incentive structure where over-requesting CU directly overpays — your CU-limit tuning logic will need revisiting when v1 lands.
